# 현재 AX 수업의 문제 분석과 개선 설계

2026-10-23 작성. 대상은 현재 문의 처리 프로젝트와 AI 튜터의 수업 운영이다. 단기 목표는 AX/AI 애플리케이션 취업 준비이며, 장기 목표인 LLM Research Engineer는 별도의 모델 학습·실험 경로로 유지한다.

**주제의 큰 순서는 유지하고, 과제 선택·설명·도움·진도 전환 방식을 바꾸는 것이 핵심이다.** 강의 한 구간의 연결된 설명을 바탕으로 기존 서비스의 기능 하나를 구현하고 결과를 해석한다. 튜터가 매 응답마다 다음 세부 과제를 만들어내는 운영은 줄인다.

2026-10-23 사용자의 “해당 설계 문서 기반 모두 구현하자” 요청에 따라 수업 운영 개선안을 채택해 기존 [ROADMAP](../../ROADMAP.md), [CURRICULUM](../../CURRICULUM.md), [학습 스킬](../../.agents/skills/study-session/SKILL.md), [학습 정책](../../.agents/references/learning-policies.md)에 반영했다. 이 문서는 분석·설계 근거이며 현행 지침의 별도 사본이나 새로운 진도표가 아니다. 현재 재개 위치는 계속 [STATE](../../STATE.md)만 정한다. 학습 중지는 유지하며, 이번 운영 반영으로 대상 학습 코드·모델 실행·미래 실습·외부 등록·게시·Git 작업을 수행하지 않는다.

**분석은 실제 산출물과 진행 대화에 근거한다.** 현재 코드와 저장 실행 결과, 현재 기준 문서, 2026-10-21의 [불만 분석](evidence/local-observations.md)과 [수업 흐름 설계](contracts/tutoring-flow.md)를 대조했다. 외부 비교에서는 공개 강의의 교안·과정 구성과 원 연구를 확인했다. 전체 영상의 설명 품질, 학습자의 실제 공부 시간, 지연 기억, 취업 성과를 측정한 것은 아니다. 아래 원인 설명은 관찰을 가장 잘 설명하는 설계 가설이며, 실제 학습 재개 뒤의 행동으로 확인해야 한다.

검토 당시 로컬 실습의 `practice/ai-apps/inquiry/service.py`는 계정 조회, 문의 선택, 문서 검색, 프롬프트 구성, 모델 호출, 출력 검사를 연결한다. `practice/ai-apps/inquiry/tools.py`에는 조회 함수와 초안 생성 함수가 있고, 초안 생성의 본 흐름 연결은 아직 다음 행동으로 남아 있다. 조회 결과를 프롬프트에 전달하는 고정 Python 흐름이며, 모델이 도구를 선택하는 agent를 구현한 상태는 아니다. 이 구현 관찰은 로컬에 보존된 실습을 대상으로 하며, 이번 문서 커밋에 해당 코드는 포함하지 않는다.

저장 로그에는 실행 101회와 서로 다른 문의 ID 18개가 있다. 반복 실행은 회귀 확인에 유용하지만 101개의 독립 문제나 학습 성과로 환산할 수 없다. 같은 문의·active 상태의 저장 결과에서는 조회 사실 누락과 근거 없는 원인 추정이 나타났으며 JSON 형식 검사는 통과했다. 결과물이 발전한 사실, 내용 오류가 남은 사실, 독립 수행이 확인되지 않은 사실을 함께 유지한다.

**최근 수업은 관련 주제를 다뤘지만, 의미 있는 결과에 비해 왕복과 부수 작업이 많아질 구조였다.** 이를 학습자의 능력이나 의지 문제로 단정하지 않는다. 새 정책 문서의 분량을 늘리는 것만으로는 같은 문제가 해결되지 않는다.

관찰을 설명하는 악순환 가설은 다음과 같다. 전체 기능과 완료 경계가 흐리면 튜터가 바로 수정할 코드 한 조각을 다음 과제로 택하기 쉽다. 학습자는 그 목적이나 연결을 다시 묻게 되고, 튜터가 작은 힌트·추가 질문·모범 코드로 대응한다. 코드와 실행 옵션은 늘지만 전체 흐름을 다시 묶는 설명은 부족해진다. 이후에는 원래 기능보다 연결 오류·표시·검사 작업이 다음 과제가 되기 쉽다. 이 연결은 학습 시간을 측정한 인과 실험 결과가 아니며, 다음 실제 기능에서 재발하는지 확인할 가설이다.

따라서 먼저 바꿀 것은 **과제의 크기와 설명의 순서**다. 그다음에 Python 보강과 지원 분담을 조정하고, 실제 출력에 근거한 피드백·종료 판단을 연결한다. 도구 교체·저장소 이전·지침 추가는 이 세 가지를 대신하는 선행 작업으로 두지 않는다.

Zoomcamp의 조회 당시 main HEAD는 공개 커밋 `1c42efbeb8141c183e7ae51698ad912c70c06a06`이었다. main의 교안과 모듈 구성을 읽고 HEAD를 확인했으며 위 링크는 해당 조회 시점을 참조한다. 비용·API·접근 조건은 실제 실행 전에 다시 확인한다. 이 확인은 강의 코드의 실행 성공이나 전체 영상 품질 검증이 아니다.

**강의를 중심에 두되, 새 강의의 전체 도구 목록을 그대로 의무화하지 않는다.** Zoomcamp는 [공식 안내](https://github.com/DataTalksClub/llm-zoomcamp/blob/1c42efbeb8141c183e7ae51698ad912c70c06a06/README.md)에서 자습 방식과 여러 도구를 소개한다. 자습에는 채점·동료 리뷰·수료증이 제공되지 않으므로 외부 피드백까지 자동 확보되는 것은 아니다. 현재 Ollama 환경을 강의의 API 호출과 바꾸면 실행 조건과 결과도 다시 확인해야 한다.

채택한 방식은 Zoomcamp의 연결된 교안 구간을 주교재로 삼고 현재 프로젝트에서 응용하는 방식이다. 실제 전체 과정을 선택하는 경우에는 해당 판본의 요구·지원·과제 정책을 별도로 따른다. 선택 구간을 참고한 자체 프로젝트 학습을 Zoomcamp 전체 수료나 공식 과제 완료로 표현하지 않는다. 영상의 언어·설명 속도·Python 부담이 본인에게 맞는지는 첫 실제 학습 구간에서 확인해야 하며, 교체 판단은 수업 전체를 초기화하는 이유가 되지 않는다.

| AI가 매번 다음 내용을 설계 | 현재 코드와 질문에 빠르게 맞출 수 있음 | 지금처럼 목적 설명·단위 선택이 흔들리면 과제가 계속 세분화될 수 있음 | 현 운영을 그대로 유지하는 안은 권하지 않음 |
| 외부 강의 전체를 순서대로 수강 | 정해진 교안·예제·과제를 일관되게 따를 수 있음 | Python 선수, 도구·실행 비용, 기존 작업과의 중복을 확인해야 함. 자습의 채점·리뷰도 별도임 | 사용자가 전체 과정을 선택할 때 가능한 대안 |
| 연결된 강의 구간과 현재 프로젝트를 결합 | 설명의 기준을 확보하고 이미 만든 서비스에서 응용할 수 있음 | AI가 다시 임의의 세부 과제를 늘리지 않도록 구간·기능·완료 경계를 먼저 정해야 함 | 현재 승인 경로를 보존하는 기본 권고안 |

강의 구간은 제목만 골라 산발적으로 인용하지 않는다. 이번 기능을 설명하는 연결된 구간을 읽고, 처음·끝과 적용할 기능을 정한 뒤 유지한다. 실제 오류나 요구 변화 없이 매 응답마다 새 자료와 목표를 추가하지 않는다.

학습 방식에 관한 근거도 적용 범위를 구분한다. [IES의 2007년 지침](https://ies.ed.gov/ncee/wwc/PracticeGuide/1)은 완성된 풀이 공부와 직접 문제 해결의 교차 배치를 중간 수준 근거의 권고로 제시한다. [PRIMM 연구](https://primmportal.com/wp-content/uploads/2020/10/teaching-computer-programming-with-primm-a-sociocultural-perspective.pdf)는 코드 읽기·관찰·수정에서 새 구현으로 이어지는 프로그래밍 수업을 다뤘다. 연구 대상은 11~14세 학교 학생이며 JS 경험이 있는 성인에게 같은 효과가 보장되는 것은 아니다. 여기서는 낯선 표현을 보자마자 빈 파일에서 추측하게 하는 방식 대신, 읽고 이해한 예에서 직접 작성으로 도움을 줄이는 설계에 참고한다.

[Bastani 외의 수학 실험](https://www.pnas.org/doi/10.1073/pnas.2422633122)과 [Kestin 외의 대학 물리 실험](https://www.nature.com/articles/s41598-025-97652-6)은 AI 지원의 설계에 따라 독립 평가 결과가 달라질 수 있음을 보여준다. 이를 근거로 AI나 영상 중 하나의 보편적 우월성을 주장하지 않는다. 이번 권고는 현재 수업의 반복된 마찰과 강의 구성·교육 연구를 함께 본 설계 판단이다.

**다음 과제는 사용자에게 보이는 변화로 선택한다.** 튜터는 과제를 제시하기 전에 내부적으로 다음을 확인한다. 이 내용을 매번 사용자에게 긴 양식으로 채우게 하지 않는다.

- 이번 기능이 해결하는 문제와 이전·이후 동작을 구체적으로 설명할 수 있는가?
- 학습자가 새로 판단하거나 구현할 핵심이 있는가? 단순 복사·표시 변경·반복 준비뿐이라면 학습 단위로 삼지 않는다.
- 그 핵심에 필요한 개념·언어 표현과 전체 데이터 흐름을 먼저 설명했는가?
- 입력과 관찰 결과, 이번에 끝낼 범위가 연결되는가? 코딩만 하고 실행·해석을 나중에 계속 미루지 않는다.
- 현재 구현을 재사용하며, 다음 기능에 필요한 결과를 남기는가? 이미 한 내용을 새 출발처럼 반복하지 않는다.

이 중 설명이 되지 않는 항목이 있으면 사용자에게 추측해서 답하게 하기 전에 튜터가 과제 범위를 고친다. 관련 파일이 여러 개라는 이유만으로 여러 수업으로 나누지 않는다. 반대로 저장·HTTP·권한·새 검색 알고리즘을 한 번에 추가해야 한다면 새 개념의 의존관계에 맞춰 기능을 줄인다. 코드 줄 수·응답 횟수·고정 학습 시간은 단위의 기준이 아니다.

**한 기능의 수업은 설명에서 결과 해석까지 이어진다.** 채택한 기본 운영은 다음 순서로 한다.

1. 튜터가 현재 코드와 저장 출력에서 이미 된 부분·실제 공백을 확인한다. 학습자는 이미 한 일을 다시 요약 제출하거나 새 진단 시험을 볼 필요가 없다.
2. 문제, 전체 흐름, 이번 결과를 하나의 연결된 설명으로 제시한다. 처음 쓰는 용어는 작은 입력과 결과를 붙여 설명한다. 필요한 원문 구간을 확인하고 직접 링크를 제공한다.
3. 낯선 개념은 기존 코드의 실제 흐름이나 별도의 작은 예제로 설명한다. 일반 API 예제는 현재 과제의 답안을 변수명만 바꾼 형태로 제공하지 않는다. 완성 예제를 읽는 활동과 새 기능을 직접 구현하는 활동을 구분한다.
4. 학습자가 핵심 기능을 작성하고 실행하며 첫 결과 해석을 한다. 제공된 공식 starter가 있는 활동은 그대로 사용하고, 새 과제를 임의의 빈 파일 재구성 시험으로 바꾸지 않는다.
5. 튜터는 실제 코드·출력·해석을 함께 검토한다. 맞는 부분은 인정하고 실제 오류·중요한 미해결을 우선한다. 구현과 결과가 연결됐다면 다음 승인 활동으로 진행한다. 문장 표현을 맞히기 위한 재질문을 하지 않는다.

일반 학습에서 대상 구현은 학습자 소유다. 자체 프로젝트의 현재 모범 답안·수정·실행 요청은 요청 범위대로 수행하고 도움받은 구현으로 구분한다. 이후 모든 구현의 상시 대행으로 확대하지 않으며, 도움 직후 같은 코드를 백지 재작성하는 시험도 강제하지 않는다. 공식 과제와 별도로 선택된 무보조 확인은 각자의 제한을 유지한다.

Python 보강은 다음처럼 관련 표현을 묶는다. 현재 전부 수강하거나 문제를 풀게 하는 새 목록이 아니라, 관찰한 공백을 설명할 때의 구성이다.

| 관찰된 필요 | 함께 설명할 내용 | 적용할 때의 기준 |
| --- | --- | --- |
| JS의 find/filter/map | 첫 항목 찾기, 조건에 맞는 목록, 항목 변환, iterator와 list의 차이 | 한 줄 축약보다 반환값과 읽기 쉬운 흐름을 우선한다. 모든 반복문을 comprehension으로 바꾸지 않는다. |
| Set으로 ID 비교 | 교집합·차집합·양방향 불일치, 순서·중복을 잃는 효과 | 누락과 초과를 구분하고 순서가 평가에 필요한지도 본다. |
| None·조건 분기 | 값 없음과 빈 값, `False`·0의 구별, 예외와 정상적인 미발견 | 현재 입력 계약이 어느 상태를 뜻하는지 먼저 정한다. |
| 모듈과 함수 재사용 | 실행 진입점과 import의 차이, 함수 참조와 호출, 입력·반환값 | 현재 역할별 패키지를 재사용한다. 폴더를 더 세분화하는 일을 별도 진도로 만들지 않는다. |
| 조회 결과와 초안 생성 | 이미 받은 값의 재사용, 부작용 없는 변환, 실제 저장·외부 변경의 차이 | 같은 상태를 왜 다시 읽는지 목적이 없으면 재조회하지 않는다. 최신성이 필요한 조회는 별도 요구로 설명한다. |

**막힌 원인에 따라 도움의 형태를 바꾼다.** 모든 상황에 “먼저 생각해봐”나 같은 질문을 적용하지 않는다.

| 학습자의 상황 | 튜터가 할 일 | 피할 대응 |
| --- | --- | --- |
| “뭘 만들라는 거야?” | 사용자·입력·원하는 결과를 구체화하고 흐름을 다시 보여준다. | 같은 지시를 다른 말로 되묻기 |
| “이 문법을 몰라” | 해당 문법을 별도의 작은 예로 설명하고 현재 코드에서 맡는 역할을 연결한다. | 긴 검색 과제나 전체 입문 강의로 돌리기 |
| 개념은 알지만 연결 위치가 불명확함 | 실제 호출 흐름에서 어느 입력이 어느 함수로 가는지 설명하고 변경할 파일의 역할을 짚는다. | 위치만 말하거나 전체 정답 코드를 먼저 제공하기 |
| 실제 학습자 디버깅 오류 | 저장 코드·오류를 확인하고 학습자의 첫 가설과 확인 방법을 한 장애에 대해 검토한다. 필요한 선수는 그 자리에서 설명한다. | 오류가 없는 단계에도 가설을 요구하거나 추측을 반복 제출하게 하기 |
| 준비 환경·제공 도구의 오류 | 허용된 준비 범위에서 튜터가 해결한다. | 설치·커널 수리를 학습 진도로 넘기기 |
| 현재 코드의 모범 답안·수정을 명시 위임함 | 허용 범위에서 작성·필요 검증하고 실제 데이터 흐름과 판단 이유를 설명한다. | 이미 명확한 요청의 재승인, 일괄 거절, 독립 구현으로 표시하기 |
| 결론이 충분히 맞음 | 부족한 비핵심 이유는 보충하고 다음 연결 활동으로 간다. | 선호하는 문장으로 다시 답하게 하기 |

같은 답을 얻기 위한 추가 확인은 현행 정책의 한 번 한도를 유지한다. 다시 혼란스럽다고 하면 예·표현·설명 단위를 바꾼다. 다음 학습 활동은 새로운 의미 있는 적용이어야 하며, 방금 받은 도움을 바로 외웠는지 검사하는 우회 시험이어서는 안 된다.

작업의 분담은 이름이 아니라 현재 학습 목적에 따라 정한다. 입력 검증도 계약 설계를 배우는 첫 기능에서는 핵심일 수 있고, 이미 아는 CLI 인자를 다시 등록하는 일은 보조일 수 있다.

| 주로 학습자가 맡는 작업 | 튜터가 맡는 지원 | 조건부로 깊게 다룰 작업 |
| --- | --- | --- |
| 기능의 핵심 분기·변환·연결, 평가 기준의 판단, 기본 학습의 대상 데이터 작성, 실행·첫 해석 | 권리 확인 원자료·허용 환경 준비, 검증된 starter·기존 코드 복구, 설명·실제 코드 리뷰, 현재 명시 위임된 반복·표시·문서 작업과 검증 | 새로운 검색 방식, 상태 보존·중복 처리, 모델 선택 agent, API·동시성·운영 품질 등 현재 목표나 실제 오류가 요구하는 내용 |

새 지원 구현의 권한은 현행 준비 정책과 해당 시점의 위임 범위로 판단한다. 이 역할 표가 요청 없는 대상 코드 수정·평가 정답 작성의 상시 권한을 만들지는 않는다.

**깊게 파는 작업에는 다음 결정을 바꿀 이유가 있어야 한다.** 문법의 짧은 사용 설명, 계약을 바꾸는 개념, 추가 실험을 구분한다.

| 진행 중인 작업 | 더 다룰 이유 | 다음으로 갈 기준 |
| --- | --- | --- |
| 문법·스타일 | 실제 오해나 반복해서 쓰는 표현이 있음 | 현재 흐름을 이해하고 적용할 수 있으면 설명을 마친다. 더 짧은 한 줄·스타일 선호는 진도 관문이 아니다. |
| 검색·답변 평가 | 변경 가설과 비교할 결과가 분명함 | 실제 결과로 검색 실패와 생성 실패, 해당 변경의 한계를 해석했으면 학습 결과가 된다. 향상이 없어도 된다. |
| 프롬프트 수정 | 누락된 정보·상충 지침 등 확인할 가설이 있음 | 수정이 새 관찰이나 구현 판단을 만들지 못하면 알려진 실패로 남긴다. 같은 사례의 표현만 계속 다듬지 않는다. |
| 상태·권한·실제 기록 | 승인 전 기록 생성, 중복 처리, 다른 대상 변경 같은 계약 위반 가능성이 있음 | 해당 기능이 주장할 동작을 실제 로컬 상태와 대조한다. 중요한 계약 위반은 그 기능 사용을 멈추고 고친다. 다른 승인 학습 전체를 무기한 중단시키지는 않는다. |
| 프레임워크·구조 확장 | 현재 구조로 표현하기 어려운 상태·재개 책임이나 실제 중복이 있음 | 이름을 배우기 위한 도입은 보류한다. 현재 Python 흐름으로 충분하면 유지한다. |

프롬프트 비교 전에는 이번에 바꿀 가설, 고정할 조건, 사용할 개발 사례와 확인할 회귀를 짧게 정한다. 최종 평가를 본 뒤 수정에 썼다면 이후 개발 자료로 취급한다. 작은 표본의 차이를 일반적 성능 개선으로 표현하지 않는다. 근거가 부족한 원인 추정은 별도 실패로 남기며 작은 모델이라는 이유만으로 원인을 확정하지 않는다.

생성 문장의 미해결 품질과 결정론적 계약도 구분한다. 예를 들어 초안에 저장하는 조회 상태는 실제 도구 결과를 사용해야 한다. 모델의 자연어 추정으로 그 필드를 바꾸는 설계는 피한다. 이는 생성 품질 문제를 숨겼다는 뜻이 아니라, 별도로 고쳐야 할 문제와 프로그램이 보장할 계약을 나누는 것이다.

**현재 위치의 복구는 초기화 없이 진행한다.** 아래는 재개 후의 연결 흐름이며, 새 과제 실행이나 AX 단위 완료 기록이 아니다. 기존 STATE의 다음 행동을 우선하고 정식 과정의 선택 범위를 임의로 건너뛰지 않는다.

별도 서비스 저장소는 초기 개발판부터 선택할 수 있다. 기능 완성·전체 AX 완료를 생성의 숨은 관문으로 삼지 않는다. 반대로 이번 학습 설계가 저장소 이전·원격 생성·공개를 실행하라는 요청은 아니다. 같은 서비스를 발전시키는 경우에는 하나의 이력을 유지하고 수업마다 새 저장소를 만들지 않는다.

한 기능의 안내는 다음 정도로 연결돼야 한다. 아래 문장은 과제 안내 방식의 예시이며 중지 중인 학습을 재개하는 지시가 아니다.

> 이번 기능은 기존 문의 처리에 초안 미리보기를 연결하는 거야. 문의 처리 중 이미 얻은 계정 조회 결과를 재사용해서, 명시적으로 초안을 요청했을 때 생성 답변과 구분된 초안을 보여주는 것이 목적이야. 지금은 초안 함수가 따로 있고 본 흐름에는 연결되지 않았어. 이번에는 그 연결과 결과 구분을 직접 구현하고, 초안을 요청한 경우·요청하지 않은 경우·조회 결과가 없는 경우의 실제 출력을 비교하면 돼. 초안 생성은 실제 접수나 계정 변경을 뜻하지 않아. 코드를 바꾸기 전에 현재 문의가 들어와 조회·검색·모델 호출·기록으로 이동하는 순서와 초안이 들어갈 위치를 먼저 설명할게.

이 안내 뒤에는 필요한 개념·실제 파일 흐름을 설명하고 구현을 기다린다. 목적 설명만 하고 “어떻게 할까?”를 되묻거나, 바로 함수의 정답 코드를 주는 방식으로 돌아가지 않는다. 실행 후에는 “완료”라는 메시지만 보고 넘어가지 않고 저장된 코드와 결과를 검토한다.

**개선 여부는 실제 수업 행동으로 확인한다.** 영상 시청 수, 테스트 개수, 생성된 코드 줄 수, 동의·완료 응답을 학습 점수로 쓰지 않는다.

스킬 구조 검사는 기존 시스템 Python의 PyYAML을 이용한 `quick_validate.py`로 통과했다. lab 환경에는 해당 검사 도구의 PyYAML이 없어 새 패키지를 추가하지 않았으며 저장소 의존성은 변경하지 않았다. 기존 테스트의 이름·설명은 문서 계약과 학습 효과를 구별하도록 고쳤고, 선택적 비교 프로토콜이 모델·추론 강도·에이전트 실행 권한을 자체 부여하지 않도록 정합화했다. 새 문구 일치 테스트나 학습 관리 도구는 추가하지 않았다.

위 운영 반영 시점에는 추가 에이전트 없이 작성자 검토로 마쳤으며 실제 모델 응답의 준수·학습 효율·독립 숙달·지연 기억은 미검증이었다. 학습 코드·자료 초기화·모델 실행·미래 기능 대행·커밋·푸시는 수행하지 않았다.

이후 사용자가 실제 효과 검증과 커밋·푸시를 요청했다. [후속 검증 결과](evidence/learning-effect-validation-2026-10-23.md)에 지원 코드의 실제 실행·공개 사본 재현 검사와 실제 학습 효과 판정에 부족한 근거를 구분했다. 첫 실제 기능의 재개 뒤 목적 명확성·지원 부담·실행/첫 해석을 관찰한다.
