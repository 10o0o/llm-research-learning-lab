# 현재 문의 과제의 목적과 대안 검토

2026-10-21 계획 검토용 제안이다. [승인 명세](../spec.md)의 FR-004~008·015~020·033~035에 대응하며 운영 ROADMAP·실습·북마크를 바꾸거나 수업을 재개한 기록은 아니다.

## 확인한 문제

현재 실행 도구 (`practice/ai-apps/inquiry_assistant.py`, 로컬 확인 자료)의 지시문은 원문에 근거한 요약·사실·추가 확인을 요구하고 조직 정책·해결 방법의 창작을 금지한다. 그러나 “처리를 위해”라는 표현만으로는 문의를 정리하는 단계인지, 실제 계정 변경을 수행하는 단계인지 확정되지 않는다.

학습자는 제공된 현상 설명이면 추가 확인이 필요 없다고 판단했고, 정보가 적은 경우에는 “어디서 로그인이 안되는지, 어떻게 안되는지”를 제안했다. 이를 계정 식별자라는 고정 정답으로 다시 유도할 근거는 없다. 현재 저장 결과는 한 개발 문의의 출력과 형식 검사이며 별도 사례 평가·실제 업무 유용성은 미확인이다.

## 문제 선택의 대안

| 대안 | 검증 가능한 기능과 근거 | 기존 작업·전체 경로와의 연결 | 판단 |
| --- | --- | --- | --- |
| 문의 접수 초안으로 범위를 좁힘 | 접수 담당자가 원문 사실과 미해결 질문을 파악하도록 정리한다. 원문 충실성·정보 보존·중복 질문·업무 범위 준수를 확인할 수 있다. | 현재 입력·출력·지원 이력을 보존하고 AX-02의 절차 근거, AX-03의 모의 접수 상태, AX-04의 서비스 품질로 연결할 수 있다. | 초기 기본 제안. 가상 입력을 쓴다는 한계를 밝히고 실제 업무 해결로 주장하지 않는다. |
| 공개 개발 문서의 질의응답 | 사용 권리를 확인한 문서에서 근거를 찾아 질문에 답한다. 출처·검색·기권의 기준을 만들기 쉽다. | AX-02와 잘 연결되지만 현재 문의의 도움·출력을 새 수행으로 옮길 수 없고 입력·평가를 새로 정해야 한다. | 근거 있는 답변이 주된 사용자 문제일 때 대안. 기존 사내비의 복제나 필수 주제로 자동 선택하지 않는다. |
| 공개 릴리스 변경 요약 | 확인한 판본의 변경에서 영향을 정리한다. 실제 변경과 요약의 누락·창작·출처를 대조한다. | 작은 AX 기능과 버전별 비교에 적합하나 도구 행동까지 확장할 이유는 별도로 필요하다. | 개발 업무와 직접 연결할 별도 문제가 있을 때 대안. 자료 권리·판본은 사용 전에 확인한다. |
| 계정 해제까지 수행하는 자동화 | 승인된 운영 절차·권한·대상 식별·실제 상태 검증이 필요하다. 현 자료로는 이 기준이 없다. | 현재의 요약·질문 기능과 책임이 다르고 실제 외부 변경은 승인 범위가 아니다. | 현재 범위에서 제외. 절차·권한·검증 환경이 갖춰질 때 다시 검토한다. |

판단 기준은 익숙한 도구 이름이나 모델 응답의 그럴듯함이 아니라 목적·접근 가능한 근거·독립적으로 확인할 결과·이전 작업 재사용·유지 비용이다. 다른 문제의 실제 사용자 필요가 확인되면 기본 제안도 바꿀 수 있다. 외부 사용자 인터뷰나 새 데이터 수집을 지금 학습의 시작 관문으로 추가하지 않는다.

## 문의 접수 초안을 선택할 경우의 평가 계약

- 담당자는 접수 내용을 읽는 사람이며 시스템의 역할은 사실 기반 초안을 돕는 것이다. 원인 확정·계정 해제·조직 정책 안내는 별도 근거가 있어야 한다.
- 사실은 원문에서 지지되는지, 요약은 중요한 조건을 보존하는지 본다. JSON 형식 통과와 내용 충실성은 별개다.
- 추가 질문은 이 처리 목적에 필요한 미해결 정보인지 판단한다. 이미 제공된 정보의 반복·목적에 불필요한 식별자 요구·근거 없는 해결 절차를 구별한다. 충분한 경우 빈 목록을 허용하고 허용 가능한 질문이 여러 가지일 수 있음을 인정한다.
- 비교 전 baseline의 역할과 기준을 정한다. 원문 그대로 전달하는 기준은 정보 보존과 압축의 차이를 보여줄 수 있지만, 그것만으로 담당자의 시간 절약이나 실제 해결률 향상을 입증하지 않는다.
- 개발 사례를 수정에 사용한 이력은 보존한다. 독립 사례·반복 시도·최종 평가를 구별하고 출력 확인 뒤 기준을 바꿨다면 새로운 사전 기준이었다고 하지 않는다. 가상 입력의 결과를 실제 고객 검증으로 표현하지 않는다.
- 학습자가 이미 제시한 판단을 같은 문장으로 다시 답하게 하지 않는다. 목적을 설명한 뒤 현재 판단을 사용해 의미 있는 구현·평가·첫 해석으로 이어질 활동을 계획한다. 위임된 CLI·검색·검사 코드는 독립 작성 근거로 세지 않는다.

이 계약은 평가 도구의 완성 코드나 새 사례의 정답표가 아니다. 학습자가 작성할 구현·평가 입력·실제 실행·첫 해석은 아직 수행하지 않았다. 계획 승인과 학습 재개 요청을 각각 확인한 뒤 해당 범위에서 적용한다.

## 개발 저장소의 시작과 포트폴리오 주장

[Zoomcamp 프로젝트 지침](https://github.com/DataTalksClub/llm-zoomcamp/blob/main/project.md)의 Tips and best practices는 프로젝트 준비 중 별도 저장소를 권한다. 최소 기능의 완성을 저장소 시작 조건으로 요구하는 근거는 확인하지 못했다. 다음 경계는 이 관찰과 사용자의 프로젝트 중심 학습 목적을 적용한 설계 판단이다.

1. **개발 공간 분리**: 독립 문제·기준 구현·환경·권리/공개 범위·기존 자료 보존 방법을 정하면 초기 개발판부터 별도 프로젝트를 시작할 수 있다. 미구현·미실행과 제공 코드는 그대로 표시한다. 첫 baseline이나 AX-04 완료를 생성의 일괄 관문으로 두지 않는다.
2. **공개와 포트폴리오 설명**: 공개 권한·자료 권리를 확인하고 실제 수행 근거만 설명한다. 작동 기능·평가/실패·실행 안내·자기 기여가 갖춰진 범위에서 포트폴리오 주장을 늘린다. 개발판을 공개했다고 작동·평가·배포가 확인된 것은 아니다.
3. **실제 작업 권한**: 이번에는 분리 기준을 계획한다. 새 저장소 생성·이전·원격 게시·배포를 수행하지 않았으며 명세·계획 승인도 이 작업들의 자동 실행 권한이 아니다.

[초기 검토](initial-review.md)의 여섯 분리 기준은 포트폴리오로 설명할 준비와 근거를 점검하는 후보로 사용한다. 이를 초기 개발 저장소를 만들기 전에 모두 통과해야 하는 시험으로 확대하지 않는다. 같은 서비스는 한 이력을 발전시키고 다른 문제·연구 질문은 독립성에 따라 추가로 분리한다.
