## Summary

목표 우선순위와 AX/RE 8단위 대응은 유지하되, 실제 기능의 목적·직접 작업 크기·사전 평가·반복 실행·산출물 누적을 구체화한다. 단순 확장자 변환이나 이전 설계의 승인 재확인으로 끝내지 않는다. [조사 결정 R-01~12](research.md), [8단위 계약](contracts/unit-audit.md), [불만별 운영 계약](contracts/tutoring-flow.md)이 상세 기준이다.

- 문의 문제는 **학습용 접수 정리**로 범위를 좁혀 조건부 유지한다. 현재 가상 입력/원문 평가 근거는 활용하고, 담당자·처리 절차·실제 업무 유용성 미확인은 보존한다. 공개 문서 Q&A·로컬 상태 조회·사내비 참고 등 대체 조건도 비교했다.
- 한 기능의 입력→직접 작성→실행→첫 해석을 작업 단위로 삼는다. 지원받은 코드·제공 CLI 사용을 독립 구현으로 세지 않는다. 최소 선수는 의존 작업 전에, 나머지는 실제 공백에서 설명한다.
- 자체 프로젝트에서 사용자가 새로 명시 위임한 수정·작성·검증은 그 범위대로 처리하고 도움과 직접 수행을 구분한다. 기본 학습의 직접 구현, 무보조 확인·공식 과제의 제한과 현재 위임을 구별해 중복 승인·일괄 거절을 막는다.
- 반복 실행은 Python 본체를 기준으로 하고 필요한 관찰에만 노트북을 쓰는 안을 제안한다. 3안의 14관점 비교·전환/중복/커널/로딩 한계를 함께 둔다. 현재 두 파일은 보존하고 새 구조를 만들지 않는다.
- AX-03은 작은 고정 흐름부터 시작한다. LangGraph는 실제 상태 보존/중단·재개 필요, single-agent 비교는 모델 주도 선택의 평가 질문이 있을 때 선택한다. 기술 사용 여부를 자동 완료 gate로 두는 현행 계약을 조정한다.
- 현재 lab 원본을 보존하고, 문제·기준 구현·환경/권리/보존 경계를 정하면 초기 개발판부터 한 서비스 repo에서 발전시킬 수 있다. 실제 기능·평가/실패·기여·재현 안내는 포트폴리오 주장의 근거이며 저장소 시작의 선행 시험이 아니다. 다른 문제/연구는 독립성에 따라 분리하며 repo 개수는 역량 근거가 아니다.
- 문서·가상 행동·실제 재개 관찰을 나눈다. 실제 학습에서의 6관점 관찰은 재개 요청 뒤에 수행하며 지금 효과 성공으로 처리하지 않는다.

## 적용 순서와 의존성

### Phase 0 — 근거와 선택 정리: 이번에 수행

승인 명세/헌법·현행 기준·001·초기 근거를 읽고 같은 feature에 setup을 수행한다. nbpeek 관련 셀/저장 출력과 CLI를 읽고 미확인 공식 구간만 순차 보강한다. 사용자 금지에 따라 스킬의 일반 연구 위임 예 대신 한 작성자가 조사한다. 공식 보강의 부분/미확인, R-01~12의 Decision/Rationale/Alternatives로 선택/보류 이유를 정리했다.

### Phase 1 — 관계·계약·검증 안내: 이번에 수행

문서 관계·8단위/튜터 계약·38요구/20제안 추적·검증 안내를 작성한다. 보호 bytes/허용 경로·표/링크/추적·공백을 확인하고 헌법 gate를 다시 대조한다. 실제 결과/미확인을 `plan-validation.md`에 기록한다. 전/후 hook 유무를 확인하고 command를 끝낸다.

### review-plan — 다음 사용자 검토 지점

상위 도우미가 같은 Run `94c571a9`의 plan 반환과 다음 review-plan 상태를 확인한다. 이 command 안에서 workflow check/run/resume을 중첩 실행하거나 엔진 파일/로그를 고치지 않는다. 사용자는 문제 유지/대체·AX-02/03 조건부 범위·도구/저장소·지원 경계를 판단할 수 있다. 명세 승인 질문을 반복하거나 명세를 Draft로 되돌리지 않는다.

### 계획 승인 후에만 할 문서 반영 순서

1. 승인된 선택으로 같은 feature의 tasks를 만들고 요구/계획/작업 정합성을 검토한다. 설계가 달라지면 영향/남은 검토를 밝힌다. 지금 작업 목록은 만들지 않는다.
2. F-01 범위/단위/산출물 계약→F-02 선수/자료→F-03 보류/복귀를 동기화한다. 역사 구간과 현재 학습 위치를 보존한다.
3. F-04 상세 경계→F-05 수업 절차→F-06 사례를 맞춘다. 기존 충분한 답/중지/준비 규칙은 유지하고 필요한 행동만 구체화한다. F-07 루트에는 최소 핵심/링크만 둔다.
4. F-08에서 바뀐 snapshot/선택만 교정하고 F-09/10 요약을 연결한다. 기준 문서보다 먼저 요약을 바꿔 다른 지시를 만들지 않는다.
5. 파일별 재독·회귀/링크/보존·필요 suite를 실행한다. 범위 밖 실패는 실제 원인/기존 변경과 나눠 보고한다. STATE·산출물·설정/lock을 검사 통과용으로 고치지 않는다.
6. 문서 반영/행동 검토를 보고한다. 학습 재개·실제 V-C·서비스 repo/게시·지원 제출은 자동 실행하지 않는다. 새 Git 권한도 생기지 않는다.

실제 재개 뒤 현재 북마크의 제공 CLI 실행/해석을 확인하고 필요한 새 기능/평가의 학습자 직접 작업으로 이어간다. repo 이전·모듈화·새 평가 데이터·훈련은 소유권과 실제 요청에 따른 후속 활동이다. 002 implement가 이를 미리 만들어 주지 않는다.

## 최종 사용 흐름

학습 재개 요청→현재 STATE/저장 근거 확인→목적/입출력/직접 작업/기준과 최소 선수 설명→허용 준비/같은 실행 경로→학습자 작성/실행/첫 해석→실제 코드/출력 피드백→다음 연결된 작업이다. 답/실행이 필요한 곳에서 기다리고 충분한 답을 다시 시험하지 않는다. 그림이 필요하면 같은 본체를 사용한 노트북, 독립 실행/공개 설명이 필요하면 그 시점의 repo 분리 조건을 검토한다. 원본/도움/실패는 유지한다.

현재 사용자가 일부 자체 프로젝트 작업을 위임하면 그 부분을 요청 범위대로 수행·검증하고 보조 수행으로 구분한다. 이 도움을 새 독립 구현 성공이나 이후 모든 대상의 상시 대행 권한으로 바꾸지 않는다.
