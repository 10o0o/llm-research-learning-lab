# 설계 조사와 제안 결정

기준일: 2026-10-21. 상태: **계획 검토용 제안, 미승인·미반영**. [승인 명세](spec.md)의 38개 요구사항과 헌법 1.0.0을 유지한다. [초기 검토](evidence/initial-review.md)·[로컬 관찰](evidence/local-observations.md)·[초기 공식 조사](evidence/official-education-sources.md)·[workflow 근거](evidence/workflow-framework-sources.md)를 출발점으로 삼았다. 새 확인 범위와 과정별 9관점은 [공식 보강](evidence/plan-source-supplement.md), 현재 파일의 추가 확인은 [계획 로컬 검토](evidence/plan-local-review.md)에 둔다.

아래 결정은 제안할 설계의 선택이다. 운영 채택·사용자 계획 승인·학습 재개·효과 검증을 뜻하지 않는다. S-01~08은 공식 보강의 출처, C-01~12는 기존 로컬 관찰의 불만, V-A/B/C는 각각 문서·행동·실제 관찰 검증이다. 모든 최종 제안의 근거/규칙/파일/이유/검증/미확인 연결은 [추적표](evidence/proposal-traceability.md)에 둔다.

## R-01 — 두 목표와 전 8단위의 대응 유지, 작업 크기·의존성 조정

**Decision**: 단기 AX와 후속 RE를 유지하고 8단위를 삭제·병합하지 않는다. 각 단위의 직접 행동은 기능의 입력부터 실행·첫 해석까지 이어지는 크기로 제안한다. [8단위 계약](contracts/unit-audit.md)에 유지/조정/착수 보류, 선수의 사용처·보강 조건, 직접 작업/도움, 산출물, 평가/실패와 연구 연결을 전수 매핑한다. RE는 장기 선택 범위로 보존하고 현재 착수는 보류한다. 현재 학습 중지는 모든 단위에 적용된다.

**Rationale**: S-01의 누적 앱, S-04의 종단 프로젝트, S-05/06/07의 모델 내부·실험 목적은 서로 다른 깊이를 보여 준다. 현재 문서의 목표 분리에는 근거가 있지만 셀·질문으로 쪼개진 진행을 개선할 구체 작업 경계가 부족하다. 실제 시간·기량·공고 적합성이 미확인이므로 단위 수를 취업 가능성·기간으로 환산하지 않는다.

**Alternatives considered**: 전체 수학/대학 과제 선행은 첫 AX 목적과 불일치. API 앱만으로 RE를 대체하면 내부 구현·학습 책임이 빠진다. 8단위를 작은 퀴즈로 더 나누는 안은 관찰된 마찰과 맞지 않는다. 거대한 앱 하나를 통째 첫 과제로 주는 안도 제외한다.

## R-02 — 현재 문의 문제는 접수 정리로 좁혀 조건부 유지

**Decision**: 학습용 기본 문제를 **접수 담당자가 문의의 현상·이미 알려진 조건·다음 확인 필요 여부를 정리하는 보조 기능**으로 명확히 하는 안을 제안한다. 실제 담당자 검증을 받은 업무 명세는 아니다. 계정 잠금 해제·조직 정책 생성·실제 계정 처리는 현재 기능의 목표로 두지 않는다. 업무 목표가 미정이면 추가 확인의 유일한 정답도 정하지 않는다. 튜터가 짧은 목적·허용 근거·평가 틀을 제안하고, 학습자에게 긴 기획 시험을 요구하지 않는다.

| 문제 후보 | 확인한 적합성 | 비용·한계 | 제안과 재검토 조건 |
| --- | --- | --- | --- |
| 현재 문의의 접수 정리 | 저장 셀의 실제 입력/응답/형식 검사, 학습자의 중복 질문 금지와 정보 부족 기준 제안이 있음 | 가상 개발 입력 3건, 담당자·업무 절차·독립 평가·실제 CLI 추론 미확인 | 초기 학습 문제로 유지·범위 조정. 평가 기준을 간단히 정하고도 유용성을 설명 못하면 다음 후보 검토. 실제 업무 절감 입증 아님. |
| 공개 사용 권리가 확인된 제품 문서 Q&A | 문서 근거·기권을 기준으로 잡기 쉽다는 설계상 이점; S-02/04의 유사 활동 | 지금 확보·권리 확인한 구체 corpus가 없고, 수집/검색 준비로 첫 결과가 늦어질 수 있음 | AX-02의 문서 필요가 생길 때 우선 대체 후보. 선택 시 자료/범위를 확인하며 현재 수업을 자동 전환하지 않음. |
| 공개 릴리스 변경 요약 | 확인한 판본의 실제 변경과 요약의 누락·창작/출처를 대조할 수 있다는 설계상 이점; 추가 공급된 문제 비교 후보 | 구체 원문/권리·판본·독립 평가 미확인, 도구 행동으로 확장할 필요는 별도 | 개발 문서 정리가 실제 사용자 문제로 확인될 때 대안. 새 자료를 지금 수집하거나 현재 입력의 결과를 새 문제 성공으로 옮기지 않음. |
| 로컬 작업 접수·상태 조회 보조 | 결과를 모의 상태와 대조하기 쉽다는 설계상 이점 | 실제 상태/권한·오류 계약을 새로 정해야 함. 현재 저장 산출물 없음 | AX-03의 유용한 조회/승인 목적이 생길 때 후보. 현재 AX-01을 대체할 필수 이유는 없음. |
| 사내비를 참고한 Q&A | 친숙한 맥락이라는 사용자/기존 설계 근거 | 원 자료 권리·팀/튜터 기여·새 평가가 미확인. 이번에 원 저장소에 진입하지 않음 | 대체 후보 보존. 원 성과 복사를 새 독립 구현으로 세지 않으며 이번 기본 문제로 자동 채택하지 않음. |
| 작은 LM·추론 최적화부터 시작 | 장기 내부 구현/측정 목적에 적합 | 지금 업무 앱을 연결할 최소 선수·자원·직접 근거가 더 필요 | RE에 유지. 첫 AX 기능의 대체로 제안하지 않음. |

**Rationale**: 기존 승인 자체가 유지 근거는 아니다. 현재 자료는 원문 근거·중복 질문을 실제로 검토할 출발점은 제공한다. 하지만 본문에 없는 정책을 답할 근거는 없다. S-04의 문제 설명·자기 자료/평가, S-06의 baseline/과업 구분을 적용하면 범위를 좁혀 확인할 수 있다. `missing_information=[]`가 항상 정답/오답인 것도 아니다.

**Alternatives considered**: 즉시 모든 자료를 버리고 새 도메인을 고르면 이미 남은 실행·기여 근거를 잃고 준비 부담이 생긴다. 반대로 현재 기능을 실제 업무에 유용하다고 확정하면 미검증 가정을 숨긴다. 더 적합한 공개 문제의 권리·평가·선호가 확인되면 같은 8단위 대응을 유지해 대체한다.

## R-03 — AX-03은 고정 흐름을 먼저, framework와 agent 비교는 필요 조건으로

**Decision**: 일반 Python의 작은 고정 흐름과 도구 계약을 먼저 이해·구현한다. 상태 보존·사람 확인·중단/재개가 실제 요구일 때 LangGraph를 한 후보로 선택한다. 모델 주도 도구 선택의 가설이 있을 때 같은 과업에서 bounded single-agent와 비교한다. framework나 agent가 없는 것을 미완료 사유로 만들지 않는 계약 조정을 제안한다.

**Rationale**: S-08의 공식 역할 설명, S-04의 도구 대체 허용, 현재 C-03/06의 목적 혼란을 함께 반영한다. LangGraph는 상태 실행에 가치가 있으나 첫 도구 하나의 선수가 되는 것은 아니다. 선택 후에는 상태·오류·권한 책임을 실제로 설명해야 한다.

**Alternatives considered**: 현행의 LangGraph/두 방식 고정 필수는 자원·과업 필요와 무관한 비용을 만든다. 모든 framework를 빼는 안은 실제 재개/상태 문제를 놓친다. 여러 framework·multi-agent·MCP를 차례로 익히는 안은 보류한다. 현재 Python 3.14 호환·API·실제 성능은 선택 시 확인하며 이번에는 설치하지 않는다.

## R-04 — Python 실행 본체, 필요한 관찰에만 노트북

**Decision**: AX 반복 실행은 Python 본체를 기본 작업 위치로 삼고, 분석·표·그림·텐서 관찰의 이점이 있을 때만 노트북을 얇게 연결하는 안을 제안한다. 아래 T-03은 두 파일의 동일 구현을 유지하자는 뜻이 아니다. 기존 노트북/스크립트는 그대로 보존하며 어떤 것도 이번에 변환·이동·실행하지 않는다. 당장은 이미 있는 CLI를 제공 도구로 구분한다. 이후 대상 기능 변경·평가 구현은 학습자가 맡는다.

같은 과업은 식별자/본문 입력→기준 구현→응답/오류→내용 판단→결과 보존이다. 비용·속도·실제 이동량은 측정하지 않았으므로 표는 구조상의 비교와 가설이다.

| 관점 | T-01 ipynb 중심 | T-02 py 모듈/프로젝트 중심 | T-03 py 본체+필요시 노트북 |
| --- | --- | --- | --- |
| 1. 복붙·화면 이동 | 함수/설정 셀 하나로 재사용 가능. 셀 분산 안내를 유지하면 왕복 발생 | 인자/설정 변경으로 실행 가능. 결과 확인 창 이동은 남을 수 있음 | 본체 호출만 재사용하면 감소 가설. 두 문서를 오가게 하면 오히려 증가 |
| 2. 커널/숨은 상태 | 변수·실행 순서·살아 있는 객체와 저장 출력 구별 필요 | 새 프로세스가 기본 경계를 드러내지만 전역·파일·서버 상태는 남음 | 노트북 커널과 본체/외부 상태 모두 관리해야 함 |
| 3. 초기화 | 준비 상태 재사용, 재시작 후 의존 셀 순서 확인 필요 | 실행마다 초기화 범위를 명시. 로딩/설정 비용 발생 가능 | 재사용 객체/설정 전달과 커널 갱신 경계가 추가됨 |
| 4. 모델 로딩 비용 | 커널 내 모델은 유지 가능, 외부 추론 서버 수명과 별개 | 프로세스 내 모델은 매번 로드할 수 있고 외부 서버는 재사용 가능 | 실제 모델 소유 프로세스/캐시가 기준. 확장자별 속도 우위 미측정 |
| 5. 관찰·시각화 | 코드·표·그림·설명을 가까이 배치하기 좋음 | 파일/터미널 결과 표시를 설계해야 함 | 본체의 결과를 필요한 표·그림으로 관찰. 새 분석 필요가 없으면 노트북 생략 |
| 6. 디버깅 | 중간 객체 확인이 쉬움, 실행 순서 재구성 부담 | 함수·stack trace·breakpoint로 입력/호출 경계 확인 | 본체 디버깅에 노트북의 오래된 import/객체 문제 추가 |
| 7. 자동평가 | 함수/외부 평가 경로로 가능. 셀 실행만으로 평가되지 않음 | 같은 입력/설정의 batch 평가 연결이 쉬움. 평가 기준은 별도 필요 | 본체 평가를 재사용, 노트북은 분석. 이중 평가 구현 금지 |
| 8. 테스트 | 함수 분리·독립 입력 필요; 저장 출력은 테스트가 아님 | 경계/회귀 검사를 함수에 연결하기 쉬움 | 본체 검사 공유, 얇은 관찰의 연결/출력 최신성 별도 확인 |
| 9. Git 변경 검토 | metadata·출력 차이가 섞일 수 있음. 의미 있는 셀/출력 보존 필요 | 텍스트 diff로 기능 변경을 비교하기 쉬움 | 코드 diff와 관찰 출력의 목적 구별. 두 본체의 동시 수정은 피함 |
| 10. 재현 | 새 커널의 순서·환경·자료·난수/서버 상태 확인 필요 | 환경·설정·입출력·외부 상태가 필요. `.py`만으로 재현 보장 안 됨 | 동일 본체/설정과 노트북 실행 순서·버전까지 연결 |
| 11. API 확장 | 재사용 함수 추출/분리가 필요할 수 있음 | 함수/계약을 API 경계에 연결 가능 | 같은 본체를 API와 관찰이 공유. 실제 서버 생성은 후속 학습 |
| 12. 학습자 기여 | 직접 작성 셀·제공 셀·실행·해석을 나눠야 함 | 제공 CLI의 실행은 직접 구현 아님. 새 대상 변경/첫 해석이 필요 | 포장/이동과 학습자 기능 변경을 구별. 도구 수는 기여가 아님 |
| 13. 준비·유지 비용 | 기존 공간 활용 이점, 커널/출력 관리 부담 | 한 파일로 시작 가능. 과한 모듈/CI는 초기 부담 | 관찰 필요가 있을 때만 비용 지출. 불필요한 두 공간 유지는 피함 |
| 14. 중복·기준 구현 | 한 노트북 안에서도 지시문/함수 중복 위험 | 본체·설정의 기준 위치 하나를 정하기 쉬움 | 노트북에 본체/지시문 복제 금지. import 갱신·동일 설정 연결 필요 |

**Rationale**: C-08/09와 저장된 두 구현의 중복, S-03의 workload 전환, S-01/05의 관찰 장점을 함께 고려했다. 혼합안을 상시 두 공간 강제로 만들지 않으면 반복 실행과 관찰 목적을 함께 다룰 수 있다.

**Alternatives considered**: T-01은 탐색의 좋은 선택이며 금지하지 않는다. 반복 실행/서비스 확장이 주목적인 현재 AX의 기본으로는 T-03을 우선한다. T-02만 고집하면 RE의 텐서/곡선 관찰을 불편하게 만들 수 있다. T-03에서 중복·커널 문제가 실제로 더 커지면 T-02로 단순화하거나 관찰 활동은 T-01로 제한한다.

거대한 골격·여러 패키지·선행 CI는 첫 유용한 결과와 무관한 준비 비용 및 튜터 대행을 늘릴 수 있어 제안하지 않는다. 한 실행 경로·필요한 입력/출력 경계 검사·결과/실패 보존부터 시작한다. 중복 기능·인터페이스 분리·회귀 필요가 실제 생기면 모듈/테스트를 늘리고, 팀/반복 배포 필요가 확인될 때 CI를 검토한다. 파일 수·소요시간·비용의 수치 비교는 미실행이다.

## R-05 — 원본을 보존하며 초기 개발부터 서비스 하나를 발전

**Decision**: 현재 lab 원본을 보존한다. 독립 문제·기준 구현·환경·권리/공개 경계·기존 자료 보존 방법을 정하면 **초기 개발판부터** 별도 AX 서비스 repo 하나에서 발전시킬 수 있다. 실제 작동 기능·평가/실패·기여·재현 안내는 **포트폴리오로 주장할 준비 기준**이며 개발 저장소 생성의 선행 시험이 아니다. 첫 baseline이나 모든 AX 완료를 분리/지원의 선수로 두지 않는다. 다른 문제 또는 연구 질문이 독립하면 소수 프로젝트/연구 repo를 검토한다. repo 생성·이전·태그·게시·배포는 이번 문서 작업에 포함하지 않는다. 이 구분은 검증 중 추가 공급된 [문제 선택/개발 공간 근거](evidence/pilot-purpose-decision.md)도 대조해 보완했다.

**Alternatives considered**: lab에 영구 고정하면 앱 독자의 독립 실행이 어려울 수 있다. 모든 기능을 새 repo로 만들면 같은 작업이 여러 결과로 보이고 수정/비교가 분산된다. 반대로 환경·권리·연구 질문이 다른 작업까지 하나에 합치면 의존성·공개 책임이 섞인다. S-04의 다른 과정 프로젝트 제출 재사용 금지를 독립 서비스 지속 발전 금지로 확대하지 않는다.

## R-06 — 허용 준비와 반복 지원을 구체화하고 핵심 대상 소유권 유지

**Decision**: 기본 학습에서는 대상 기능/평가 데이터/실행/첫 해석을 학습자가 맡는다. 환경·검증된 기존 코드 복구·결과 표시·반복 실행의 기존 제공 도구처럼 **현재 대상이 아닌 지원**은 현행 권한 안에서 준비한다. 준비 셀 수동 복사나 같은 준비 범위의 재승인을 요구하지 않는다. 명시 위임·제공/기존 코드·API/개념 도움·직접 작성·직접 실행·독립 확인을 별개로 표현한다.

자체 프로젝트에서 사용자가 새로 명시한 수정·작성·검증 위임은 그 요청 범위의 최신 지시로 처리한다. 이미 명확히 요청한 지원에 중복 승인을 요구하거나 기본 학습 원칙만으로 일괄 거절하지 않는다. 도움받은 작업은 보조 수행으로 표시하고 독립 구현·학습자 실행의 근거로 세지 않는다. 과거 위임만으로 이후 모든 핵심 대상의 대행 권한을 추정하지 않으며, 공식 과제와 무보조 확인의 별도 제한은 해당 활동에 적용한다. 이번 문서 검토 자체가 새 실습 대행 요청은 아니다.

**Rationale**: C-04/05/10과 저장 셀/CLI의 도움 표시, S-03/05의 제공 도구, S-06/07의 공식 과제 제한을 함께 반영한다. 기본 직접 구현과 최신 명시 지시의 관계는 [헌법 Governance](../../.specify/memory/constitution.md#governance)의 사용자 명시 요청 우선 원칙을 따른다. 공식 과제의 제한을 자체 프로젝트의 모든 도움 요청에 확대하지 않고, 과거 명시 요청에 따른 도움을 지우거나 새 숙달로 만들지 않는다.

**Alternatives considered**: 모든 오류/표시/반복을 학습자가 매번 백지 작성하는 안과 요청 없이 모든 대상 기능을 튜터가 대신 만드는 안 모두 제외한다. 명시 위임을 무시하거나 과거 도움을 미래 핵심 대상 대행의 상시 권한으로 확대하지 않는다. 공식 과제에는 개별 더 엄격한 정책을 적용한다. 도움 뒤에는 현재 목적에 맞는 다음 직접 활동으로 연결하며 같은 코드를 즉시 무보조로 다시 쓰게 하는 통과 관문을 추가하지 않는다.

## R-07 — 추가 질문의 정답보다 먼저 업무 목적과 충분성 정의

**Decision**: 평가 전 역할·처리 단계·제공 정보·허용 근거·기대 행동을 짧게 제시한다. 형식, 원문 사실성, 중복 질문, 그 단계의 추가 확인 필요, 업무 유용성을 나눠 본다. 목표가 정해지지 않으면 여러 타당한 해석을 남기고 ID 같은 항목을 유일한 정답으로 강요하지 않는다.

**Rationale**: C-06/11/12의 실제 불만/판단과 S-04의 문제 설명, S-06의 과업/평가 명시를 연결한다. 최신 충분성 판단은 사용자 제공 사실이고 새 모델/사례 평가 결과는 아니다. 빈 목록도 목적과 원문에 따라 판단한다.

**Alternatives considered**: 튜터가 생각한 누락 목록을 맞히게 하는 방식, 응답을 본 뒤 필요한 필드를 덧붙여 채점하는 방식, 질문이 많을수록 좋은 결과라는 방식은 제외. 사전 기준을 수정할 필요가 생기면 그 비교는 개발 검토로 다시 표시한다.

## R-08 — 충분한 답을 인정하고 실제 공백만 피드백

**Decision**: 현행 study-session의 같은 답 추가 확인 한 번 제한·이후 설명/표현 변경·충분한 답 수용·연결된 다음 활동 원칙은 유지하고 이행을 교정한다. 같은 결론을 선호 문구로 다시 말하게 하지 않는다. 실제 오류일 때만 변경 전 가설/확인 방법을 검토한다. 출력은 입력·응답·형식/내용의 차이·실패 위치를 읽기 쉽게 연결한다.

**Rationale**: C-03/04/06/07과 현행 규칙/저장 출력의 차이가 근거다. S-01의 전체 구조, S-06의 이해/명확성 피드백은 실제 근거에 대한 설명이라는 비교점이다. 질문 횟수나 능력 부족을 원인으로 단정하지 않는다.

**Alternatives considered**: 모든 설명 뒤 새 퀴즈, 도움 뒤 즉시 같은 답 재시험, 이미 있던 규칙을 길게 반복 추가하는 방식은 제외. 문서에 없는 행동 기준만 사례로 보강한다. 가상 응답이 좋아도 실제 불편 감소는 미확인이다.

## R-09 — 평가를 작업 전에 정하고 형식·내용·행동·실제 효과를 분리

**Decision**: [단위 평가표](contracts/unit-audit.md#공통-평가와-단위별-비교-설계)에서 과업·독립 표본·개발/최종 역할·baseline·변경/고정 조건·실패/미실행을 사전 정의한다. 현재 개발 입력 3건과 그 반복 시도는 최종 평가가 아니다. 변경 전 출력은 합성하지 않는다. 새 평가 데이터·실행·첫 해석은 재개 후 학습자가 한다.

**Rationale**: C-11/12의 실행 한계, S-03의 코드/모델 검사 분리, S-04의 검색/응답 평가, S-06의 실험 조건/실제 결과가 근거다. 검색 corpus 색인과 평가 질의/qrels 선택, 학습 전처리 fit과 train/dev 선택을 구별한다.

**Alternatives considered**: JSON pass를 내용 품질로 세기, 반복 횟수를 독립 사례 수로 세기, 최종 사례를 보고 수정한 뒤 미사용 test라 하기, loss 감소/agent 성공 문구만으로 결론 내리기 모두 제외. 실제 미개선도 해석한 결과이며, 실행 불가와는 다르다.

## R-10 — 조기 지원 근거·주 서비스·연구 결과를 나눔

**Decision**: 작은 실제 기능과 여섯 설명(문제·직접 기능·평가/실패·재현·기여/도움·한계)이 있으면 조기 공고 비교에 쓴다. 주 포트폴리오는 같은 서비스의 누적 발전이다. RE는 모델 내부/학습/제한 재현의 별도 깊이다. 외부 운영·지원 제출·현재 채용 적합성을 확인한 것으로 보고하지 않는다.

**Rationale**: C-01/03과 현행 지원 경계, S-04의 독자용 README/재현, S-06의 기여/실험 설명에 맞는다. 기존 JD는 과거 목적 표본이다. 새로운 시장 전수 조사를 하지 않았고 현재 공고·학위/연차 요건은 별도 원문 확인 대상이다.

**Alternatives considered**: 모든 RE/외부 배포 완료까지 지원을 미루기, 제공 CLI/팀 코드를 본인 독립 구현으로 포장하기, repo 개수로 적합성 판단하기는 제외. 독립 수행 미확인을 지우지 않고 재현/출처 설명으로 다룬다.

## R-11 — 북마크의 의미를 검사하고 특정 활동 문구 고정은 해제

**Decision**: 후속 구현에서 기존 테스트의 보존/공개/소유권 부분을 유지하되 `test_state_is_a_public_bookmark_with_one_next_action_and_preserved_original`의 AX-01·식별자/본문·직접 작성/실행 고정과 현재 상태에 대한 `미실행` 필수 문구를 분리한다. 유효한 현재 단위 참조·다음 행동 하나·근거/미확인의 정직성·금지 정보·과거 인용 보존을 검사한다. 후속 단위/평가/해석 북마크도 통과하고 복수 다음 행동·사적 정보·없는 단위는 실패하는 검증을 설계한다.

**Rationale**: 현재 tests 550~568행은 실제 다음 행동이 바뀌어도 첫 학습 표현을 요구한다. 82~97·331~437행에는 계속 유지할 준비/대상/문서 도움·행동 검토 분리도 있다. S-03의 검사 목적 구분과 S-04의 재현 관점에 비춰 특정 스냅샷 대신 계약 회귀를 확인해야 한다.

**Alternatives considered**: 테스트 전체 삭제·STATE를 옛 문구로 되돌려 통과·아무 단위도 검증하지 않기 모두 제외. `test_first_baseline_has_its_own_completion_boundary`의 입력/형식/미실행 경계는 유지하고 R-02의 과업 범위와만 대조한다. 기본 직접 학습·무보조 확인·CS336의 제한을 유지하면서 R-06의 새 명시 위임과 도움 분류도 검사한다.

## R-12 — 문서 반영·응답 행동·실제 재개 관찰을 별도 검증

**Decision**: V-A는 문서/링크/보존·요구 대응, V-B는 동등한 가상 상황의 응답 행동, V-C는 학습자가 재개를 요청한 실제 활동 한 단위 이상에서 수동 관찰한다. V-C의 6관점·실패/미실행 판정은 [검증 안내](quickstart.md)에 둔다. 새 진도표·시간표·평가 DB를 만들지 않는다.

**Rationale**: 현재 불만은 실제 진행에 관한 것이며 문구 검사는 그것을 측정하지 못한다. 헌법 IV·기존 테스트의 행동/교육 효과 분리와 일치한다. 공식 과정의 rubric도 개인 효과의 인과 입증은 아니다.

**Alternatives considered**: 가상 응답/정적 검사만으로 개선 완료 선언, 과거 복붙 횟수/학습 시각 추정, 테스트를 위해 수업·모델을 대신 실행하기는 제외. 현재 baseline이 없으므로 개선율은 만들지 않는다. 계획/문서 승인도 수업 재개가 아니다.
