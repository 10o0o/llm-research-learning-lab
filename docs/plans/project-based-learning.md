# 강의와 프로젝트를 연결하는 학습 계획

작성일: 2026-10-30 · 상태: 운영 문서에 반영한 설계 이력

이 문서는 앞선 조사·검토와 사용자의 주 30시간 이상 학습 의사를 정리한다.
운영 문서 반영은 2026-10-30 [구현 계획·적용 기록](project-based-learning-implementation.md)에 따라 수행했다.
아래 내용은 설계 당시의 범위와 예상 일정이다. 현재 경로·자료는 ROADMAP·CURRICULUM을 따른다.
문서 작성은 새 강의 선택, 프로젝트 착수, 실습 수행 또는 진도 변경이 아니다.
현재 선택과 다음 행동은 [STATE](../../STATE.md), 현재 운영 규칙은 [AGENTS](../../AGENTS.md)가 기준이다.

## 1. 목표와 유지할 학습 방식

단기에는 기존 개발 경험을 활용해 AX / AI 애플리케이션 직무에서 설명할 수 있는 프로젝트를 만든다.
장기에는 모델의 학습·평가·실험과 추론·시스템으로 깊이를 넓혀 LLM Research Engineer 역량을 쌓는다.
첫 집중 구간은 주 30시간 × 12주, 약 360시간을 가정한다. 시작 날짜는 아직 정하지 않았으며,
주차는 상대적인 작업량 추정이다. 12주 수료·취업·CS336 진입을 보장하는 일정이 아니다.

학습은 다음 흐름을 유지한다.

1. 허브와 에이전트가 현재 위치, 큰 흐름, 공식 자료의 정확한 구간을 안내한다.
2. 학습자가 선택한 강의·공식 과제의 순서에 따라 외부 실습 공간에서 작성·실행한다.
3. 현재 코드·결과에 필요한 기초를 설명받고, 첫 해석을 바탕으로 리뷰·수정을 이어간다.
4. 실제 수행·도움·막힘과 다음 행동을 STATE에 연결한다.

포트폴리오 적용은 공식 강의에서 배운 내용을 자기 문제로 확장하는 작업이다.
에이전트가 강의를 대체하는 자체 수업이나 정답 코드를 먼저 만들지 않는다.
한 세션의 활성 범위는 하나로 두고, 공식 단원 실습과 자기 프로젝트 적용을 구분한다.
보충 설명은 현재 범위로 돌아오기 위한 것이며 별도의 필수 선수 과정으로 늘리지 않는다.

## 2. 자료의 역할

| 자료 | 이 계획에서의 역할 | 선택·범위의 경계 |
|---|---|---|
| LLM Zoomcamp 2026 | 현재 주자료. 검색·생성·Agent·평가·모니터링을 공식 순서로 이어간다. | 현재 선택을 유지한다. 강의 예제와 자기 도메인의 프로젝트는 구분한다. |
| Karpathy Zero to Hero | 모델 기반의 우선 후보. tensor·학습·언어모델 구현을 연결한다. | 보관된 자기 코드와 도움 이력을 먼저 확인한다. 처음부터 전체 재수강하지 않는다. |
| MIT 6.S191 2026 | 신경망·미분·시퀀스 등 필요한 개념을 짧게 보충한다. | 전체 완주를 프로젝트의 선행 조건으로 두지 않는다. 실습 세 개를 독립 포트폴리오 세 개로 세지 않는다. |
| PyTorch 공식 튜토리얼 | 지금 쓰는 tensor·autograd·학습 루프의 API 참고. | 설치된 버전에 맞춰 해당 부분만 확인한다. |
| ML Zoomcamp 2026 | 전통 ML 모델링이 필요한 경우의 대안. | 현재 병행 필수 과정이 아니다. |
| CS336 Spring 2026 | 모델 구현·시스템·연구 실험의 후속 심화 후보. | PyTorch·딥러닝·수학·시스템 경험과 자원을 확인한 뒤 선택한다. 공식 도움 정책을 따른다. |

강의의 공개 연도와 목적 적합성을 함께 본다. 기초 개념이 유효한 기존 자료·자기 코드는 재사용한다.
MIT와 Karpathy를 동시에 완주하는 의무를 만들지 않는다. 모델 기반 구간을 시작할 때 주자료와
실제 수행 범위를 정하며, 여기의 추천 목록을 STATE의 선택으로 자동 복사하지 않는다.

## 3. 현재 위치에서 이어가는 12주 초안

작성 시 STATE의 활성 자료는 LLM Zoomcamp 2026이며 재개 위치는 Module 5 / 4강이다.
세부 구현·실행의 확인 범위는 STATE를 다시 읽는다. 이 문서의 스냅샷으로 최신 진도를 덮어쓰지 않는다.

| 구간 | 공식 학습과 직접 수행할 범위 | 예상 산출물 |
|---|---|---|
| 1~2주 | Monitoring 4~14강을 현재 위치부터 이어간다. 기존 코드·환경을 재사용하고, 자기 프로젝트의 사용자·공개 데이터·평가 질문을 고른다. | 기존 모니터링 실습 결과, 첫 프로젝트 범위와 초기 질문 |
| 3~4주 | Zoomcamp 프로젝트 지침을 기준으로 자기 데이터의 ingestion → retrieval → answer를 구성한다. Module 2·4의 자기 코드와 자료를 필요한 만큼 참조한다. | 실행 가능한 첫 버전, 고정 평가셋, 기본 검색과 개선안 비교 |
| 5~6주 | 실패 원인을 수정하고 재현 방법·API·실행 환경·비용·지연과 사용 피드백을 정리한다. | 지원 자료로 설명할 첫 프로젝트, 데모와 비교 결과 |
| 7~8주 | 다음 실험에 필요한 모델 기반을 기존 Karpathy 기록에서 연결한다. 필요한 경우 MIT·PyTorch 자료의 해당 부분을 보충하고 추론 기준선을 만든다. | 필요한 개념과 연결된 실행, 두 번째 실험의 조건과 기준선 |
| 9~12주 | 추론 실험 하나에 집중하고 같은 조건에서 변경 전후를 비교한다. | 재현 가능한 실험, 성능·품질 비교와 실패·한계 설명 |

Monitoring은 공식 4~14강을 기본 예상 범위로 한다. 6·7모듈은 공식 선택 자료이므로
이번 계획의 필수 완주 항목으로 추가하지 않는다. 모듈 숙제와 capstone 요건은 해당 원문으로 확인하며,
이 표가 공식 숙제 완료·제출 또는 수료 기준을 대체하지 않는다.

첫 프로젝트가 아직 실행·평가·재현되지 않으면 두 번째 실험의 시작을 늦춘다.
첫 결과를 제시할 수 있는 시점부터 관련 공고와 대조해 지원 자료를 정리한다.
주차가 지났다는 이유로 완료를 기록하거나 다음 단계로 자동 진급하지 않는다.

## 4. 첫 프로젝트: 자기 도메인의 근거 기반 RAG 서비스

기본 후보는 특정 제품의 기술지원 문서에서 근거를 찾아 답변하는 서비스다.
제품·데이터·언어는 아직 미선정이다. 공개·재사용이 가능한 한 도메인으로 범위를 좁히고,
일반적인 질문 답변보다 그 문서를 검색해야 하는 실제 사용자 문제를 고른다.
학습자가 고른 데이터로 시작하며 강의 FAQ 데이터는 공식 프로젝트용으로 사용하지 않는다.

공식 프로젝트 범위와 취업용 확장을 구분한다.

| 구분 | 범위 |
|---|---|
| Zoomcamp 공식 프로젝트의 중심 | 자기 지식베이스, ingestion, 검색, 근거 기반 답변, 검색·전체 흐름 평가, 사용 가능한 인터페이스, 재현성·문서 |
| 이 계획에서 제안하는 추가 증거 | API, 재현 가능한 실행 환경, 지연·비용·오류 측정, 실패 분석과 변경 이유, 데모·사용 피드백 |
| 첫 범위에 포함하지 않는 것 | 다중 사용자·로그인·복잡한 Agent·대규모 인프라·모델 미세조정을 한꺼번에 추가하는 작업 |

공식 지침에서 모니터링과 실제 배포는 필수 항목이 아니다. 위 확장을 강의의 필수 숙제로 부르지 않는다.
기존 Streamlit·검색·평가 코드 중 이해한 부분을 재사용한다. 새 기술은 필요한 동작을 위해 선택한다.
로컬에서 재현 가능한 실행과 데모를 먼저 만들 수 있으며, 공개 서비스 배포는 별도 실행 범위다.

리뷰할 근거는 다음과 같다. 점수판이나 새로운 수강 자격시험을 만들기 위한 항목이 아니다.

- **문제·데이터:** 사용자, 필요한 답변, 데이터 출처·이용 조건과 수집·갱신 방법을 설명한다.
- **평가:** 직접 검토한 초기 30~50문항에서 시작한다. 기대 근거를 남기고 조정용과 최종 확인용을 구분한다. 문항 수 자체가 평가의 충분성을 보장하지 않는다.
- **개선:** 기본 검색과 개선 1~2개를 같은 조건에서 비교한다. 검색 실패·잘못된 근거·근거 없는 답변을 구분하고 LLM 채점 일부를 직접 검토한다.
- **실행:** 다른 사람이 준비·실행 방법을 따라갈 수 있게 한다. 정상 질문, 근거가 없는 질문, 주요 실패 경로를 실제 결과로 확인한다.
- **운영:** 전체 응답 시간과 LLM 호출 시간의 측정 구간을 구분하고 비용·오류·피드백을 남긴다. 가상 시나리오와 실제 사용 결과도 구분한다.

평가를 본 뒤 최종 확인용 질문에 맞춰 반복 튜닝했다면 그 결과를 독립적인 최종 평가로 부르지 않는다.
개선이 없거나 악화된 경우도 조건·해석과 함께 남긴다. 높은 수치를 미리 약속하지 않는다.

## 5. 두 번째 실험: 기존 임베딩 추론 실습의 확장

기본 후보는 기존 ONNX 임베딩 실습을 재사용하는 작은 추론 실험이다.
같은 모델을 PyTorch와 ONNX에서 비교할 수 있는지 먼저 확인한다.
가능하지 않으면 모델 변환을 새 대형 과제로 늘리지 않고 배치 크기 등 한 변경축으로 범위를 줄인다.
이 단계에서도 공식 자료의 선택 구간을 바탕으로 필요한 개념과 실행 방법을 익힌다.

- 모델·tokenizer·pooling·정규화, 입력·장비·실행 버전을 기록한다.
- 측정 목적에 따라 바꿀 축 하나를 정하고 다른 조건을 맞춘다.
- 준비·예열과 측정 구간을 구분해 반복 실행하고 지연·처리량·메모리를 비교한다.
- 임베딩 결과와 검색 품질도 확인해 속도와 품질의 관계를 설명한다.
- 기준선, 후보, 재현 방법, 실패·변동·장비 한계를 실습 레포에 남긴다.

모델·장비·예산과 공식 참고 구간은 착수 시 확인한다. GPU 구매·유료 실행은 이 계획의 전제가 아니다.
이를 생성형 LLM 서빙 전체, 분산학습 또는 CS336 과제 완료로 표현하지 않는다.
후학습에 대한 관심과 실제 필요가 더 크다면 그 시점에 방향 하나를 다시 정하고 동시 수행하지 않는다.

임베딩 추론 실험은 모델 학습 기반을 모두 다루지 않는다. 장기 모델·연구 경로로 넘어갈 때는
선택한 자료에서 loss·gradient·학습 루프·학습/검증 분할을 직접 다루는 경험을 별도로 연결한다.

## 6. 시간·도움·포트폴리오 운영

주 30시간의 초기 배분은 구현 18시간, 평가·디버깅 5시간, 필요한 이론 5시간, 문서·지원 자료 2시간이다.
고정 의무 시간표가 아니라 시작 가정이며 작업 성격에 따라 조정한다. 결과는 실험 때 바로 남긴다.
이론은 현재 동작·결과를 이해하는 데 필요한 설명부터 충분히 다룬다.

학습자는 핵심 설계·구현·실행·첫 해석을 맡는다. 에이전트는 공식 자료 안내, 개념·API 설명,
오류 분석, 작은 확인 방법, 실제 작업 리뷰와 확인된 진도 저장을 돕는다.
이미 수행한 내용을 반복 시험하거나 매 세션 퀴즈·회고·별도 계획서 작성을 요구하지 않는다.
익숙한 주변 작업은 맡긴 범위에서 도울 수 있고, 자체 실습의 구현 대행을 명시적으로 요청한 경우
그 도움 범위를 보존한다. 공식 과제의 더 엄격한 정책은 항상 해당 과제에 적용한다.

프로젝트의 코드·실험·README는 학습자 소유 외부 레포에 둔다. README에는 문제, 데이터 출처,
실행법, 설계 이유, 평가 조건·비교, 실패·한계, 데모, 주요 도움 범위를 연결한다.
공식 프로젝트 동료평가용 README는 영어로 준비한다. 이력서에는 실제 수행과 측정한 결과만 쓴다.
허브에는 자료·현재 진도·외부 근거 링크만 두며 새 프로젝트 이력 DB·TIL 의무·점수판은 만들지 않는다.
학습 성과는 구현·실험 근거와 연결하고, 취업 성과로 자동 확대하지 않는다.

## 7. 적용 전 남은 선택과 근거

운영 문서 적용은 아래 선택이 미정이어도 진행할 수 있다. 해당 실습을 시작하기 전 필요한 항목만
짧게 확인하고, 선택 전에는 실제 수강·저장소·비용·수행 사실로 기록하지 않는다.

- 첫 프로젝트의 사용자·제품·공개 데이터와 실제 사용할 외부 실습 공간
